 SMART XEROX Product Requirements &amp; UX Design Specification QR-based document upload • Customer-wise orders • Operator-controlled printing Product vision A customer scans a Xerox shop's QR code, uploads documents from their phone (including files shared or saved from WhatsApp), enters their name, chooses optional print preferences, and submits one order. The shop operator reviews the files, edits the print settings if needed, confirms the final job and prints. Version 1.0 | 30 October 2026 | Concept / MVP specification 1. Product summary Smart Xerox is a mobile-first web platform for local Xerox and print shops. Each shop receives a unique QR code. Customers scan it and submit documents through a browser—no customer app installation, WhatsApp number sharing, or email hand-off is required. User Primary goal What they do Customer Send documents to the correct shop quickly Scan QR, enter name, upload files, set optional preferences, submit order, see order reference/status. Shop operator Receive clean, grouped orders and control the final print job Review customer folder, preview/download files, edit settings, confirm, print, update status. Shop owner/admin Configure and operate the shop Register shop, manage staff/printers, create QR code, set default options/pricing, review orders and reports. 2. Goals and non-goals MVP goals Give every registered shop a unique QR code and shop-specific upload page. Allow customers to upload multiple supported files in one order from a mobile browser. Group all files under a customer order using the customer's entered name and a unique order number. Let customers provide optional print preferences, while clearly stating that the operator confirms the final settings. Give operators the ability to edit all four print settings before confirming: print type, paper size, copies and sides. Keep a visible order lifecycle: New → In review → Confirmed / Printing → Completed (or Cancelled / Needs clarification). Protect uploaded documents with shop-level access control and configurable retention. Out of scope for first MVP Direct WhatsApp account integration or automatic reading of WhatsApp messages. Customers can use the phone's file picker to select files they have saved or shared from WhatsApp. Automatic silent printing without operator confirmation. Universal direct integration with every printer model and driver. Online payments, OCR, AI document classification, multi-branch routing and customer accounts (can be later phases). 3. User stories and acceptance criteria US-01 — Open the correct shop page As a customer, I want to scan the QR code displayed at a Xerox shop so that my documents reach that shop. Acceptance criteria: QR URL contains a unique, non-guessable shop identifier; page displays shop name and location/branch label; inactive shops cannot accept new orders; customer does not need to create an account. US-02 — Identify my order As a customer, I want to enter my name so the operator can identify my order. Acceptance criteria: Name is required; allow common letters, spaces and reasonable punctuation; show a privacy note that the name is visible to shop staff; generate a unique order number independently. US-03 — Upload multiple documents As a customer, I want to select multiple documents from my phone so I can submit everything together. Acceptance criteria: Support multiple files; show selected file names, file sizes and upload progress; allow remove/retry; validate file type and size; handle upload failure without losing already selected files where possible. US-04 — Choose optional print preferences As a customer, I want to express my preferred print settings without being forced to understand every option. Acceptance criteria: Show four simple preference groups: Color/B&amp;W, paper size, copies, single/double-sided; provide sensible shop defaults; label choices as preferences subject to operator confirmation. US-05 — Submit and track order As a customer, I want confirmation after submission so I know the shop received my files. Acceptance criteria: Prevent duplicate submissions on repeated taps; show order number and submitted summary; show current status; do not promise a completion time unless the shop provides one. US-06 — Review customer folder As an operator, I want each order grouped under the customer's name so I can process it without searching through loose files. Acceptance criteria: Dashboard lists newest orders first; each order card shows customer name, order ID, file count, time and status; opening an order shows its files in one order-specific folder; files can be previewed or downloaded. US-07 — Edit final print settings As an operator, I want to change any customer preference because customers may select an incorrect option or may not know what they need. Acceptance criteria: Operator can edit all four settings before confirmation; original customer preferences remain available for comparison/audit; final settings are clearly distinguished; changes are saved before print confirmation. US-08 — Confirm and process As an operator, I want to confirm the final settings and process the order so the shop retains control. Acceptance criteria: Confirmation screen summarizes file list and final settings; operator must explicitly confirm; status changes are timestamped; operator can mark completed or flag a problem. US-09 — Manage shop and QR As a shop owner, I want to manage my shop profile and QR code so customers submit to the correct location. Acceptance criteria: Owner can view/download/print QR; QR is shop-specific; owner can pause incoming orders; staff access is restricted to their shop. US-10 — Protect customer documents As a customer and shop owner, I want uploaded documents to be private and removed when no longer needed. Acceptance criteria: Only authorized staff for that shop can access files; use HTTPS and private object storage; use expiring access links; configure retention and deletion; record access and status changes. 5. Data model (initial) Entity Important fields Notes Shop id, name, slug/qr_token, branch_label, status, created_at Each QR resolves to exactly one shop. Use random token, not sequential IDs. ShopUser id, shop_id, name, email/username, password_hash, role, status Roles: OWNER, OPERATOR. Enforce shop_id scope on every request. PrintOrder id, public_order_number, shop_id, customer_name, status, submitted_at, updated_at Customer name is not unique. Use UUID/ULID or database ID internally. OrderFile id, order_id, original_filename, storage_key, mime_type, size_bytes, page_count, upload_status Keep files private; do not expose raw storage paths. CustomerPreference order_id, print_type, paper_size, copies, sides Immutable snapshot of customer-requested values. FinalPrintSettings order_id, print_type, paper_size, copies, sides, updated_by, updated_at Operator-approved values; preserve history if changed multiple times. OrderEvent id, order_id, actor_id, event_type, old_value, new_value, created_at Audit trail for status and setting changes. 9. For a small prototype, multipart upload through Spring Boot is acceptable with strict limits. 10. Business rules and edge cases Shop-specific isolation: an operator must never access another shop's orders or files. Customer preferences are optional. If omitted, show the shop's configured defaults and require operator confirmation. Operator final settings must be supported by the shop's configured printer capabilities; unsupported settings should be disabled or flagged. Customer can upload several files, but each order has one common setting set in the MVP. Per-file settings can be a later enhancement. File validation: allow a defined safe list (initially PDF, JPG/JPEG, PNG; DOC/DOCX only if the shop's workflow can render them reliably). Reject executable files and unsupported types. Set limits for total order size, per-file size, file count and page count. Display limits before upload. Handle password-protected PDFs, corrupted files, zero-byte files and files that cannot be previewed. Do not automatically print immediately after upload. Operator review and confirmation are mandatory in MVP. Use idempotency for order submission so a slow network or repeated tap does not create duplicate orders. Use retention controls: e.g. configurable auto-delete after a shop-defined period; clearly disclose this to customers. Provide a manual fallback: operator can download files and print using the normal application/driver if direct print automation is not yet integrated. 11. Security, privacy and reliability Serve all pages and uploads over HTTPS. Store uploaded files in private storage; use short-lived signed URLs for preview/download. Scan uploads for malware where practical; never execute uploaded content. Apply file-type validation using actual content/MIME inspection, not filename extension alone. Rate-limit public QR endpoints and upload attempts; use CAPTCHA or abuse controls if needed. Use random, non-sequential QR tokens and order receipt tokens. Enforce shop-level authorization on every operator API and file request. Log order access, settings edits, status changes and file deletion without logging document contents. Define a privacy notice explaining that documents are shared with the selected shop for printing and deleted according to the shop's retention policy. 12. Recommended MVP delivery plan Sprint Scope Definition of done Sprint 1 — Foundation Shop registration/admin, shop QR token, customer upload page shell, operator login A test shop can generate a QR and open its public upload page. Sprint 2 — Orders and files Customer name, multi-file upload, validation, order creation, order number, private storage A customer can submit an order and operator can see the files. Sprint 3 — Operator workflow Order list, customer-wise order detail, preference display, editable final settings, audit history Operator can edit four settings, save and confirm. Sprint 4 — Status and polish Order statuses, search/filter, responsive UI, error states, retention job, security testing End-to-end test passes on Android phone and shop desktop. Later — Print automation Local print agent, printer capability discovery, spooler integration, supported printer testing Validated printing for specific printer models; fallback remains available. 13. MVP success measures Customer can submit a multi-file order in under two minutes on a typical mobile connection. Operator can identify and open a new order without searching WhatsApp or email. Operator can change all four final settings before confirming. Every order and file is isolated to the correct shop. Duplicate order creation is prevented on retry/double tap. Operator can complete the print using the shop's existing print workflow even if automation is not available. 14. Decisions to confirm before implementation Decision Recommended MVP default Settings scope One set of four settings applies to all files in an order; individual file settings later. Customer preferences Optional, prefilled from shop defaults; operator can change them. Folder model One folder per order, displayed as “Customer name — Order #”. Same customer can have multiple orders. Payment Pay at counter; online payment later. Customer account No account required; order receipt number is enough for MVP. Notifications On-screen receipt first; SMS/WhatsApp notifications later only if shop opts in. File formats PDF, JPG/JPEG and PNG first; add Office files after reliable conversion/preview is available. Printing Manual operator print in MVP; automate only after validating target printer models. Recommended product decision Use one order folder per submission, not one permanent folder per customer. A person may visit multiple times or submit different jobs; order-level folders prevent old documents and print settings from being mixed. 15. Final product statement Smart Xerox replaces the informal “send your files to our WhatsApp number/email” process with a shop-specific QR code and a structured print-order workflow. Customers upload documents and submit preferences in seconds. Operators receive customer-wise order folders, retain full control over the final print settings, confirm the job and update its status. The first release focuses on reliable order intake and operator workflow; hardware-level print automation is a later, printer-specific phase. End of specification
